## Phase 3: derive `TASK_BRIEF`

### Canonical source URL

Remove fragments and unnecessary query parameters. Preserve the final canonical
HTTPS URL, canonical origin, and observed redirect chain. Do not retain tokens,
sessions, or private identifiers in the URL.

### Site ID

Derive it in this order:

1. a short ASCII slug of the official product name;
2. otherwise, the brand component of the registrable domain;
3. remove `www`, company suffixes, and meaningless generic words;
4. require the result to match `[a-z0-9][a-z0-9-]*`; and
5. check the current repository for collisions.

When the same site ID already exists:

- For the same source origin, set `existing_site=true`. Do not reinitialize or
  overwrite it; plan an evidence refresh/repair for the existing site.
- For a different source origin, create a stable suffix from an official product
  qualifier and record the reason for the collision.

### Display name

Determine it in this order: `og:site_name`, schema.org Organization/Product,
header/logo, page title, then registrable domain.

### Target identity

Derive automatically:

```text
SITE_DIR=materials/<site-id>
TARGET_ORIGIN=https://<site-id>.website-bench.com
WORKER_NAME=websitebench-<site-id>-demo
```

### Site purpose

Use the home-page call to action, product pages, and official help center to
describe the core business purpose in one sentence:

```text
Help <primary users> complete <core task> and obtain <primary result>.
```

Do not use a marketing slogan without verifiable meaning.

### Roles

Always consider anonymous users. Include another role only when official pages
or documentation explicitly establish it and it changes pages, permissions, or
flows. For every role, record:

- ID and display name;
- whether authentication is required;
- `directly-observed`, `structural-only`, `inferred`, or `unavailable`;
- evidence URLs;
- pages, data, or permissions it changes;
- whether Live View is required; and
- whether an existing entitlement is required.

Do not add admin, seller, premium, editor, or another role merely because sites
of this type commonly have one.

### Core journeys

Select the smallest initial journey set that represents core business value and
resolves major implementation ambiguity. Do not prescribe a count in advance or
classify every discovered feature as P0. Base selection on:

- the primary home-page call to action;
- the product's core entity;
- prominence in primary navigation;
- official onboarding/help documentation;
- whether it directly serves the site purpose;
- whether it contains a critical state change; and
- whether it has success, failure, and recovery semantics.

Every journey contains:

- `id`;
- P0/P1 priority;
- role;
- purpose;
- preconditions;
- starting URL;
- steps;
- expected result;
- failure variant;
- recovery variant;
- `source_mutation_required`;
- evidence kind and evidence URLs; and
- confidence.

Do not invent exact fields, error copy, or submission results from search
snippets. A formal Browserbase trace must freeze those facts.

The `core_journeys` here are scope-planning objects generated by the Agent from
evidence, not formal human trace text. They may only identify which traces to
request from a human and guide capture-plan design. Never automatically copy a
journey's `purpose` or `steps` into `human_trace_text`.

### Page families

Build the initial page families from primary navigation, sitemaps, calls to
action, and journeys:

- public/marketing;
- discovery/list/search;
- entity detail;
- creation/edit;
- account/auth;
- settings;
- role-specific; and
- error/recovery.

This is initial scope that source capture must correct; do not claim it is
already complete.

### Locale, timezone, and viewport

Determine locale from `<html lang>`, an official locale selector, date/currency
formatting, and the primary market. When it cannot be determined, temporarily
use `en-US` and record the issue in `unresolved`.

When the source explicitly shows an account, regional, or entity timezone,
record the corresponding policy. Otherwise use:

```json
{
  "timezone": "Etc/UTC",
  "timezone_policy": "temporary deterministic default; re-freeze from Browserbase evidence"
}
```

Do not infer a business timezone from company headquarters alone.

Initial viewports are:

- desktop: 1440×900;
- mobile: 390×844; and
- one tablet viewport when public CSS, the viewport meta tag, or observed
  responsive behavior reveals an important intermediate breakpoint.

These are initial anchors, not a maximum count. During formal capture, adjust
and freeze them according to real source breakpoints, layout discontinuities,
and core-journey needs.

### Deterministic seed plan

Generate the smallest synthetic, nonsensitive data plan from the core journeys:

- test roles;
- core business entities;
- empty and populated states;
- failure/retry states;
- an isolation actor;
- enough entities for content density and pagination; and
- reset, restart, and duplicate-submission probes.

Describe only entity types and synthetic examples. Do not copy real users,
private data, or source-account content.

### External services

List observed authentication, maps, search, email, upload/storage, payment,
analytics, support/chat, and other APIs. For each, record:

- evidence kind;
- whether the clone needs a local adapter;
- whether it creates an external side effect;
- whether user authorization is required; and
- whether the formal runtime must have zero remote dependencies.

### Authority

Authority is not a network fact. Even when a site supports email, subscriptions,
or payments, keep these defaults:

```json
{
  "authorized_source_mutations": [],
  "requested_source_mutations": [],
  "real_email_authorized": false,
  "stripe_test_authorized": false,
  "live_payment_authorized": false,
  "push_authorized": false,
  "pr_authorized": false,
  "public_deployment_authorized": false,
  "rights_or_redistribution_status": "unknown",
  "authentication_access": "request-human-live-view",
  "credentials_persisted": false
}
```

When a journey requires a source-site write, list the exact operation only in
`requested_source_mutations`; do not put it in the authorized list. When
authentication or a human demonstration is required, create adaptive
`trace_acquisition` candidates instead of immediately marking the evidence
permanently unavailable or hard-coding every handoff in the initial brief.

### Evidence and confidence

For every derived field, record:

- evidence URLs;
- a short observation;
- `directly-observed`, `structural-only`, `inferred`, or `unavailable`;
- `high`, `medium`, or `low` confidence;
- whether formal Browserbase capture must refreeze it; and
- an unresolved reason, when applicable.

When official sources conflict, prefer the directly observed current source
page, record the conflict in `unresolved`, and choose the most conservative
initial scope and authority.

This schema is only a prompt handoff, not an official WebsiteBench gate schema,
and cannot serve as technical-verification evidence.

Every item in `trajectory_recording.recordings` uses the following shape. It
records the source and boundary of **structural evidence**, not human source
text and not visual evidence:

```json
{
  "trace_id": "tr-001",
  "side": "source|clone",
  "human_trace_text_id": "ht-001",
  "environment": "human-local|capture",
  "runtime_identity": {
    "browser": "<name/version>",
    "viewport": "<w>x<h>",
    "locale": "",
    "timezone": ""
  },
  "allowed_origins": [],
  "output_dir": "materials/<site-id>/artifacts/trajectory/<trace-id>",
  "session_status": "complete|stopped|failed",
  "counts": {"actions": 0, "screenshots": 0, "dropped_events": 0},
  "credential_segment": "not-recorded|discarded",
  "screenshots_enabled": false,
  "establishes": ["routes", "redirects", "selectors", "step-order", "form-actions"],
  "does_not_establish": ["pixels", "copy", "network-closure", "cross-origin-iframes"],
  "uncertainty_resolved": []
}
```

Count trajectories from the `human-local` environment separately from evidence
from the `capture` environment. A trajectory cannot support anything listed in
`does_not_establish`; refreeze that evidence in the capture environment when
needed.

Every item in `human_trace_texts` must use the following shape. When there is no
human source text, leave the array empty; never fill it with an Agent
suggestion, page copy, or a placeholder:

```json
{
  "human_trace_text_id": "ht-001",
  "text": "<verbatim text provided or explicitly selected by the human>",
  "text_sha256": "<SHA-256 of the UTF-8 source text>",
  "provided_at": "<UTC ISO-8601>",
  "source": "initial-user-input|live-user-message|human-selected-inventory",
  "source_ref": null,
  "status": "confirmed"
}
```

`source_ref` stores only a nonsensitive source identifier such as a workbook or
task ID. If text may contain private or sensitive values, have the human provide
a sanitized version before persistence; never write it first and sanitize it
later. When the human later changes text, create a new version, recalculate the
hash, and invalidate capture plans bound to the old hash. Never overwrite the
historical source text and continue using the old trajectory identity.

Also output a concise `DERIVATION_SUMMARY` listing each field, derived value,
evidence grade, confidence, and whether Browserbase must refreeze it.

After plan approval, or after site initialization outside plan-only mode, save
the final brief to:

```text
materials/<site-id>/scope/derived-task-brief.json
```

Record important derivation decisions and corrections in a safe lifecycle
record, preferably through `--message-stdin`. Never record secrets, Live View
URLs, session IDs, private data, or raw network bodies.
